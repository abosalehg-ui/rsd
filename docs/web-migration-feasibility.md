# 🛰️ دراسة جدوى: تحويل «رصد» من تطبيق محلي إلى موقع إلكتروني

> **الحالة:** مسودّة للمراجعة — تحديث أغسطس 2026
> **النطاق:** نقل منصة رصد (OSINT) من التشغيل المحلي (سطح المكتب / Docker محلي) إلى خدمة ويب متاحة عبر الإنترنت.
> **القرار المعتمد في هذا التحديث:** **الواجهة على Vercel + الخادم على AWS** (معمار مفصول عبر رابط API). التفاصيل في القسمين 4 و 5.

---

## 1. الخلاصة التنفيذية

**التحويل ممكن تقنيًا ومنخفض التكلفة، والبنية الحالية جاهزة له إلى حدٍّ كبير.** الواجهة (Frontend) مبنية كموقع ثابت (Static SPA) قابل للنشر مباشرة على منصات الاستضافة الثابتة، والخادم (Backend) خدمة FastAPI خفيفة تعمل داخل Docker. أكبر تغيير مطلوب ليس في الكود بل في **البنية التشغيلية**: نطاق (Domain)، شهادة HTTPS، وكيل عكسي (Reverse Proxy)، وتأمين الخادم.

**القرار المعماري (بعد تقييم البدائل في القسم 3.5):**

| المكوّن | القرار | السبب المختصر |
|---|---|---|
| **الواجهة (Frontend)** | **Vercel** | واجهة Vite ثابتة؛ Vercel يعطي بناءً تلقائيًا + CDN عالمي + معاينات لكل PR، وأفضل من GitHub Pages. |
| **الخادم (Backend)** | **AWS (الاستضافة الحالية)** | عملية دائمة التشغيل (FastAPI + جدولة + SQLite). لا يمكن استضافتها على Vercel أو GitHub. استغلال استضافة مدفوعة قائمة بدل دفع مورّد ثالث. |
| **الربط بينهما** | **رابط API عبر HTTPS** | `VITE_API_BASE` في Vercel يشير إلى `https://api.rasd.<domain>` — مدعوم في الكود أصلًا. |

**لماذا لا الخادم على Vercel/GitHub؟** لأنّ رصد يحتاج **عملية دائمة** تجمع البيانات في الخلفية (APScheduler) وتكتب في قاعدة على القرص (SQLite) — وهذا نموذج «خادم» لا «موقع ثابت/Serverless». التفصيل في القسمين 3 و 3.5.

## 2. الوضع الحالي (نقطة البداية)

### 2.1 البنية التقنية

```
┌─────────────────────────────┐        ┌──────────────────────────────┐
│  Frontend (React 18 + Vite) │  HTTP  │  Backend (FastAPI / Python)  │
│  - Leaflet 2D + globe.gl 3D │ ─────► │  - REST API (/api/*)         │
│  - PWA (يعمل دون اتصال)     │ polling│  - APScheduler (جمع دوري)    │
│  - i18n عربي/إنجليزي        │        │  - SQLite (aiosqlite)        │
│  - بث مباشر: تضمين YouTube  │        │  - ETag caching middleware   │
└─────────────────────────────┘        └──────────────┬───────────────┘
                                                       │ يجلب من مصادر خارجية
                          ┌────────────────────────────┼─────────────────────────┐
                       GDELT   NewsAPI   RSS   UCDP   OpenSky(ADS-B)   Iran OSINT
```

### 2.2 حقائق تقنية مؤثّرة في القرار

- **الواجهة ثابتة بالكامل (Static SPA + PWA):** تُبنى إلى `dist/` وتُخدَّم كملفات — لا تحتاج خادم تطبيقات. تدعم بالفعل متغيّر `VITE_API_BASE` لتوجيه الطلبات إلى Backend خارجي (`frontend/src/utils/api.js`).
- **التواصل عبر الاستطلاع الدوري (polling) لا WebSocket:** `usePolling` يستدعي REST كل 30 ثانية. **هذا يبسّط الاستضافة كثيرًا** — لا حاجة لجلسات ثابتة (sticky sessions) ولا اتصالات دائمة.
- **البث المباشر = تضمين YouTube (`youtube-nocookie`) من جهة العميل.** لا يمرّ عبر خادمنا → **صفر استهلاك عرض نطاق للخادم** من البث. (ملاحظة: `cobalt` منفصل تمامًا عن رصد.)
- **قاعدة البيانات SQLite ملف واحد على القرص.** ممتازة لنسخة واحدة منخفضة الحِمل، لكنها لا تدعم الكتابة المتزامنة من عدة عمليات — نقطة يجب مراقبتها عند التوسّع.
- **الجدولة تعمل داخل عملية الـ Backend نفسها** (APScheduler in-process). أي أنّ الخادم يجب أن يبقى **قيد التشغيل دائمًا** ليجمع البيانات — وهذا حجر الأساس في قرار الاستضافة.
- **CORS مفتوح حاليًا (`allow_origins=["*"]` في `backend/app/main.py`)** — يجب تقييده بنطاق Vercel عند النشر.
- **Dockerfile الخادم يشغّل uvicorn بـ `--reload`** (وضع تطوير) — يجب تغييره لأمر إنتاجي.

### 2.3 طرق التشغيل المدعومة اليوم

مثبّت ويندوز (PyInstaller + Inno) · Docker Compose · تشغيل تطوير محلي · GitHub Pages (الواجهة فقط). أي أنّ **نصف الطريق مقطوع مسبقًا**: الواجهة جاهزة للنشر الثابت، والخادم يعمل داخل Docker جاهز للترحيل.

## 3. لماذا لا يصلح GitHub لاستضافة الـ Backend؟

| قدرة GitHub | تستضيف الـ Backend الحيّ؟ | السبب |
|---|:---:|---|
| **GitHub Pages** | ❌ | يقدّم ملفات ثابتة فقط (HTML/JS/CSS). لا يشغّل Python ولا يفتح منفذًا للاستماع. |
| **GitHub Actions** | ❌ | بيئة مؤقتة (ephemeral) للمهام القصيرة، تُدمَّر بعد انتهائها، بحد أقصى 6 ساعات، وبلا عنوان دخول (inbound) ثابت. غير صالحة لخادم دائم. |
| **GitHub (Repo/CI)** | ✅ (دوره الصحيح) | التخزين، البناء الآلي (CI)، والنشر الآلي (CD) إلى AWS و Vercel. |

> **الخلاصة:** رصد يحتاج **عملية دائمة** (خادم HTTP + جدولة + قاعدة بيانات على القرص). هذا نموذج «خادم» لا «موقع ثابت»، وGitHub لا يوفّره. **الاستضافة على AWS، وGitHub يبقى مصدر الكود وخط الأنابيب.**

## 3.5 مقارنة منصّات الاستضافة (تقييم البدائل)

قُيّمت أربع منصّات لكلٍّ من الواجهة والخادم؛ الخلاصة أدناه هي أساس القرار المعتمد.

### للواجهة (Static SPA)

| المنصّة | الملاءمة | الحكم |
|---|---|---|
| **Vercel** | بناء تلقائي من Git + CDN عالمي + معاينات PR + HTTPS تلقائي | ✅ **المُختار** — الأفضل للواجهة |
| GitHub Pages | نشر ثابت مجاني (يعمل حاليًا) | بديل مقبول، لكن بلا معاينات PR وبتحكّم أقل |
| AWS (نفس الخادم) | خدمة `dist/` خلف Caddy | ممكن، لكنه يضيف حِملًا على خادمك ويفوّت CDN Vercel |

### للخادم (FastAPI + جدولة + SQLite)

| المنصّة | تشغّل الجدولة الدائمة؟ | ملاحظات على رصد | الحكم |
|---|:---:|---|---|
| **AWS (الحالية)** | ✅ | خادم دائم تملكه أصلًا؛ SQLite على قرص دائم؛ صفر تكلفة خادم إضافية | ✅ **المُختار** |
| Render / Railway | ✅ (بخطة Always-on مدفوعة) | الخطة المجانية **تنام عند الخمول** فتتوقّف الجدولة؛ القرص مؤقّت فيضيع `rasad.db` (يلزم Volume مدفوع أو Postgres مُدار) | بديل جيّد لكنه **مورّد + تكلفة إضافية** بلا داعٍ ما دامت AWS موجودة |
| DigitalOcean Droplet | ✅ | خادم خام (VPS) مثل EC2 تمامًا — لا يقدّم ميزة على AWS التي تملكها | لا داعي له |
| Vercel | ❌ | Serverless: لا عملية خلفية دائمة (الجدولة تسقط)، ونظام ملفات مؤقّت (SQLite يضيع)، ومهلة تنفيذ قصيرة | غير صالح للخادم |

> **الاستنتاج:** النمط المعماري «فصل الواجهة عن الخادم عبر API» صحيح ومحترف. لكن اختيار **Render/Railway للخادم يعني استئجار خادم ثانٍ** بينما تملك خادم AWS دائمًا يعمل. لذا: **الواجهة على Vercel، والخادم على AWS**. (يُنظر في Render/Railway فقط لو كانت الأولوية «أقل جهد تشغيلي والابتعاد عن إدارة EC2»، مقابل ~7$+/شهر وترحيل محتمل إلى Postgres.)

## 4. المعمار المعتمد: Vercel (واجهة) + AWS (خادم)

```
                 المستخدم / المتصفّح
                        │
          ┌─────────────┴──────────────┐
          │ HTTPS                       │ HTTPS  (طلبات /api فقط)
          ▼                             ▼
┌────────────────────┐        ┌──────────────────────────────────┐
│  Vercel (CDN عالمي) │        │  AWS EC2  (18.133.11.77 / لندن)   │
│  الواجهة الثابتة    │        │  ┌────────────────────────────┐  │
│  (build من Vite)    │        │  │ Caddy — HTTPS تلقائي        │  │
│  VITE_API_BASE ─────┼────────┼─▶│ api.rasd.<domain> → :8000   │  │
└────────────────────┘  API    │  └──────────────┬─────────────┘  │
                               │        ┌────────▼──────────┐     │
                               │        │ rasad-backend      │    │
                               │        │ FastAPI :8000      │    │
                               │        │ + APScheduler      │    │
                               │        │ + SQLite (volume)  │    │
                               │        └───────────────────┘     │
                               │  ┌─────────────────────────────┐ │
                               │  │ cobalt (حاوية معزولة، حدود)  │ │
                               │  └─────────────────────────────┘ │
                               └──────────────────────────────────┘
```

**خصائص هذا المعمار:**
- **الواجهة على Vercel:** لا تبني الواجهة على خادمك — Vercel يبنيها من Git وينشرها على CDN. يزول عبء «Dockerfile إنتاجي للواجهة» بالكامل.
- **الخادم على AWS:** ينقل كما هو داخل Docker؛ Caddy أمامه يعطي HTTPS تلقائيًا لنطاق الـ API فقط.
- **الأصلان مختلفان (Vercel ≠ AWS):** لذا **CORS إلزامي** ويُضبط بنطاق Vercel تحديدًا (لا `*`). هذه هي المقايضة الوحيدة مقابل بساطة Vercel.

## 5. المتطلّبات التقنية لنقل الخادم إلى AWS

### 5.1 البنية التحتية على AWS (إعداد لمرّة واحدة)

| المتطلّب | التفصيل في حالتك | ضروري؟ |
|---|---|:---:|
| **نطاق فرعي للـ API** | مثل `api.rasd.<yourdomain>` → سجل **A record** يشير إلى `18.133.11.77`. يلزم لشهادة HTTPS ولربط Vercel بالخادم. | ✅ |
| **Elastic IP** | تثبيت `18.133.11.77` (منطقة لندن `eu-west-2`) كي لا يتغيّر عند إعادة التشغيل. مجاني ما دام مرتبطًا. | ✅ |
| **شهادة HTTPS** | Let's Encrypt عبر **Caddy** (تلقائية بالكامل). مجانية. إلزامية (الواجهة على HTTPS لا تستدعي API عبر HTTP). | ✅ |
| **Reverse Proxy** | **Caddy** أمام الخادم يوجّه `api.rasd.<domain>` → `rasad-backend:8000`. أبسط من Nginx+certbot. | ✅ |
| **Security Group** | فتح **80/443** للعالم؛ **22 (SSH)** مقيّد بعنوانك؛ **إغلاق 8000** عن الخارج (يصله Caddy داخليًا فقط). | ✅ |
| **قرص/Volume دائم لـ SQLite** | ضمان كتابة `rasad.db` على مسار دائم (مجلد مُركَّب / EBS) لا داخل طبقة الحاوية المؤقتة. | ✅ |
| **حدود موارد Docker** | `mem_limit` / `cpus` لكل حاوية لعزل رصد عن `cobalt`. | ✅ |
| **نسخ احتياطي** | مهمة cron يومية تنسخ `rasad.db` وترفعها إلى S3 (أو snapshot لـ EBS). | ✅ موصى بشدّة |

### 5.2 تعديلات الكود المطلوبة (صغيرة — للتنفيذ لاحقًا عند القرار)

> ملاحظة: هذه الوثيقة تخطيطية فقط؛ لم تُكتب أي أكواد بعد. القائمة أدناه ما سيُنفَّذ عند الموافقة.

| # | الملف | التغيير | لماذا |
|:-:|---|---|---|
| 1 | `backend/app/main.py` | استبدال `allow_origins=["*"]` بنطاق **Vercel** فقط، يُقرأ من متغيّر بيئة (مثل `CORS_ORIGINS`). | الواجهة على أصل مختلف؛ الحالي يفتح الـ API للجميع. |
| 2 | `backend/Dockerfile` | حذف `--reload`، وتشغيل uvicorn بأمر إنتاجي **بعامل واحد (worker=1)**. | `--reload` وضع تطوير؛ وعامل واحد ضروري لأنّ **SQLite + الجدولة لا يحتملان عدّة عمّال** (تعارض كتابة + تكرار الجدولة). |
| 3 | `.env` (على الخادم لا في Git) | ضبط `DATABASE_URL` على مسار داخل الـ **volume الدائم** + مفاتيح `newsapi_key` / OpenSky الحقيقية + `CORS_ORIGINS`. | بقاء البيانات عبر إعادة النشر، وتشغيل المصادر، وتقييد CORS. |
| 4 | `docker-compose.yml` | إضافة خدمة **Caddy**، توحيد مسار الـ volume مع `DATABASE_URL`، وحدود الموارد. **(إزالة خدمة الواجهة — تنتقل إلى Vercel.)** | الواجهة لم تعد تُبنى على الخادم؛ Caddy يتولّى HTTPS والتوجيه. |
| 5 | Vercel (لوحة الإعدادات، لا كود) | `VITE_API_BASE = https://api.rasd.<domain>/api` + ربط المستودع (مجلّد `frontend`). | كودك يدعم `VITE_API_BASE` أصلًا — لا تعديل كود، فقط متغيّر بيئة. |

> **ملاحظة مقابل النسخة السابقة من هذه الوثيقة:** لم يعد مطلوبًا «Dockerfile إنتاجي للواجهة» ولا خدمة الواجهة في compose — لأنّ **Vercel يتولّى بناء الواجهة ونشرها**. هذا تبسيط ناتج عن اعتماد Vercel.

### 5.3 تقدير الموارد (الحِمل الفعلي)

رصد **خفيف جدًّا**؛ العبء الأساسي نداءات شبكة خارجية دورية لا حوسبة:

| المورد | الاستهلاك المتوقّع | ملاحظة |
|---|---|---|
| **الذاكرة (RAM)** | ~150–400 MB للخادم + ~30 MB لـ Caddy | صغير جدًّا |
| **المعالج (CPU)** | خامل معظم الوقت؛ نبضات قصيرة عند الجمع | لا يزاحم `cobalt` إن وُضعت الحدود |
| **القرص (Disk)** | قاعدة بيانات نصية تنمو ببطء (~عشرات–مئات MB/سنة) + ~200 MB للحاويات | لديك ~40 GB متاح → وفرة كبيرة |
| **عرض النطاق (Bandwidth)** | صادر: استجابات JSON صغيرة فقط (الواجهة تُخدَم من Vercel لا منك؛ البث لا يمرّ عبرك) | منخفض جدًّا |

> **التعايش مع `cobalt`:** محمّل الفيديو كثيف على **عرض النطاق والقرص** بشكل متقطّع. يجب:
> - عزله في حاوية منفصلة بمنفذ مختلف.
> - وضع `mem_limit`/`cpus` لكلٍّ منهما.
> - مراقبة القرص: تنزيلات `cobalt` قد تملأ الـ 40 GB وتُعطّل كتابة SQLite. **يُنصح بتنظيف دوري لمخرجاته** أو فصلها على مجلد بحصّة (quota).

## 6. اعتبارات التوسّع والأمان (عند الفتح العام)

### 6.1 قاعدة البيانات SQLite — متى تصبح عنق الزجاجة؟
- ممتازة لنسخة واحدة وقراءات كثيرة (نمط رصد الغالب: يجمع الخادم، ويقرأ الزوّار).
- **قيدها:** كاتب واحد في اللحظة. مع الجدولة المستمرة + زوّار كثيرين قد تظهر `database is locked`.
- **التوصية:** ابدأ بـ SQLite (يعمل الآن). جهّز مسار ترحيل إلى **PostgreSQL** إن تجاوزت البيانات ملايين الصفوف أو الزوّار العشرات المتزامنين. SQLAlchemy يجعل الترحيل مباشرًا.

### 6.2 حدود مفاتيح API الخارجية
- **NewsAPI (المجاني):** ~100 طلب/يوم وبيانات متأخّرة 24 ساعة — قد لا تكفي موقعًا عامًّا؛ قد تلزم ترقية.
- **OpenSky:** حصص للحساب المجاني؛ الجمع كل 30 ثانية.
- **ميزة تصميمك:** الجمع مركزي في الخادم لا من متصفّح كل زائر → **الحصص لا تتضاعف بعدد الزوّار**.

### 6.3 الأمان
- HTTPS إلزامي (Let's Encrypt عبر Caddy).
- تقييد CORS بنطاق Vercel، وتقييد SSH.
- إخفاء `/docs` (Swagger) أو حمايته في الإنتاج إن لم يكن مطلوبًا للعامة.
- تحديد معدّل الطلبات (rate limiting) على مستوى Caddy لمنع الإساءة.
- لا مصادقة مستخدمين حاليًّا — إن أردت لوحة خاصة، يلزم إضافة طبقة تسجيل دخول (خارج نطاق التحويل الأساسي).

### 6.4 القانوني/الأخلاقي
- عند النشر العام، راجع شروط استخدام كل مصدر (GDELT/NewsAPI/UCDP) بخصوص إعادة النشر، وأضف نسب المصادر (attribution) في الواجهة.

## 8. مصفوفة القرار: أين يعيش كل مكوّن؟

| المكوّن | القرار المعتمد | البديل |
|---|---|---|
| **مصدر الكود + CI/CD** | GitHub (Repo + Actions) | — |
| **الواجهة (Static)** | **Vercel** (CDN + معاينات PR) | GitHub Pages (مجاني، أبسط، بلا معاينات) |

## 10. الخلاصة والتوصية

1. **التحويل مُجدٍ وموصى به** — البنية جاهزة تقريبًا، والتكلفة الإضافية ضئيلة.
2. **الواجهة على Vercel + الخادم على AWS**، مربوطان عبر رابط API. هذا يجمع سرعة Vercel للواجهة مع استغلال استضافة AWS المدفوعة القائمة للخادم الدائم.
3. **لا الخادم على Vercel/GitHub** (Serverless/ثابت لا يشغّل الجدولة الدائمة ولا يحفظ SQLite)، **ولا استئجار Render/Railway** ما دامت AWS تعمل — إلا إذا فُضّلت بساطة الإدارة مقابل تكلفة إضافية.
4. **الأولوية التقنية الأولى:** النطاق الفرعي `api.rasd.<domain>` + Caddy (HTTPS) + تقييد CORS بنطاق Vercel + Dockerfile إنتاجي (worker=1) + ضبط `VITE_API_BASE` في Vercel. هذه هي الفجوة الحقيقية بين «يعمل محليًّا» و«موقع عام آمن».
5. **راقب لاحقًا:** حصص API الخارجية، وقفل SQLite عند نمو الزوّار — مع مسار ترحيل جاهز إلى PostgreSQL.

> **بعبارة واحدة:** انشر الواجهة على Vercel، وانقل الخادم كما هو إلى AWS داخل Docker مع Caddy لـ HTTPS تلقائي، قيّد CORS بنطاق Vercel، واعزل cobalt — تحصل على «رصد» موقعًا إلكترونيًّا بأقلّ تغيير في الكود وأقلّ كلفة.
