# 🛰️ دراسة جدوى: تحويل «رصد» من تطبيق محلي إلى موقع إلكتروني

> **الحالة:** مسودّة للمراجعة — يوليو 2026
> **النطاق:** نقل منصة رصد (OSINT) من التشغيل المحلي (سطح المكتب / Docker محلي) إلى خدمة ويب متاحة عبر الإنترنت.

---

## 1. الخلاصة التنفيذية

**التحويل ممكن تقنيًا ومنخفض التكلفة، والبنية الحالية جاهزة له إلى حدٍّ كبير.** الواجهة (Frontend) مبنية كموقع ثابت (Static SPA) وتنشر أصلًا إلى GitHub Pages، والخادم (Backend) خدمة FastAPI خفيفة تعمل داخل Docker. أكبر تغيير مطلوب ليس في الكود بل في **البنية التشغيلية**: نطاق (Domain)، شهادة HTTPS، وكيل عكسي (Reverse Proxy)، وتأمين الخادم.

**الإجابة المباشرة على السؤالين الجوهريين:**

| السؤال | الإجابة المختصرة |
|---|---|
| **أين يُستضاف الـ Backend — GitHub أم AWS؟** | **AWS.** الـ Backend عملية دائمة التشغيل (خادم + قاعدة بيانات + جدولة). GitHub لا يستضيف خوادم حيّة — فقط ملفات ثابتة (Pages) و CI/CD (Actions). دور GitHub يبقى: التخزين، البناء، والنشر الآلي. |
| **هل استضافة AWS الحالية تكفي؟** | **نعم بوفرة.** رصد تطبيق خفيف جدًّا (SQLite + FastAPI). المساحة المتبقية (~40 GB) والموارد كافية، بشرط عزله عن `cobalt` بحدود موارد واضحة. |

## 2. الوضع الحالي (نقطة البداية)

### 2.1 البنية التقنية

```
┌─────────────────────────────┐        ┌──────────────────────────────┐
│  Frontend (React 18 + Vite) │  HTTP  │  Backend (FastAPI / Python)  │
│  - Leaflet 2D + globe.gl 3D │ ─────► │  - REST API (/api/*)         │
│  - PWA (يعمل دون اتصال)     │ polling│  - APScheduler (جمع دوري)    │
│  - i18n عربي/إنجليزي        │        │  - SQLite (aiosqlite)        │
│  - بث مباشر: تضمين YouTube  │        │  - ETag caching middleware   │
└─────────────────────────────┘        └──────────────┬───────────────┘
                                                       │ يجلب من مصادر خارجية
                          ┌────────────────────────────┼─────────────────────────┐
                       GDELT   NewsAPI   RSS   UCDP   OpenSky(ADS-B)   Iran OSINT
```

### 2.2 حقائق تقنية مؤثّرة في القرار

- **الواجهة ثابتة بالكامل (Static SPA + PWA):** تُبنى إلى `dist/` وتُخدَّم كملفات — لا تحتاج خادم تطبيقات. تدعم بالفعل متغيّر `VITE_API_BASE` لتوجيه الطلبات إلى Backend خارجي.
- **التواصل عبر الاستطلاع الدوري (polling) لا WebSocket:** `usePolling` يستدعي REST كل 30 ثانية. **هذا يبسّط الاستضافة كثيرًا** — لا حاجة لجلسات ثابتة (sticky sessions) ولا اتصالات دائمة.
- **البث المباشر = تضمين YouTube (`youtube-nocookie`) من جهة العميل.** لا يمرّ عبر خادمنا → **صفر استهلاك عرض نطاق للخادم** من البث. (ملاحظة: `cobalt` منفصل تمامًا عن رصد.)
- **قاعدة البيانات SQLite ملف واحد على القرص.** ممتازة لنسخة واحدة منخفضة الحِمل، لكنها لا تدعم الكتابة المتزامنة من عدة عمليات — نقطة يجب مراقبتها عند التوسّع.
- **الجدولة تعمل داخل عملية الـ Backend نفسها** (APScheduler in-process). أي أنّ الخادم يجب أن يبقى **قيد التشغيل دائمًا** ليجمع البيانات — وهذا حجر الأساس في قرار الاستضافة أدناه.
- **CORS مفتوح حاليًا (`allow_origins=["*"]`)** — يجب تقييده بنطاق الإنتاج عند النشر العام.

### 2.3 طرق التشغيل المدعومة اليوم

مثبّت ويندوز (PyInstaller + Inno) · Docker Compose · تشغيل تطوير محلي · GitHub Pages (الواجهة فقط). أي أنّ **نصف الطريق مقطوع مسبقًا**: الواجهة تنشر للويب، والخادم يعمل داخل Docker جاهز للترحيل.

## 3. لماذا لا يصلح GitHub لاستضافة الـ Backend؟

هذه أهم نقطة في الدراسة، لأنّ الالتباس شائع.

| قدرة GitHub | تستضيف الـ Backend الحيّ؟ | السبب |
|---|:---:|---|
| **GitHub Pages** | ❌ | يقدّم ملفات ثابتة فقط (HTML/JS/CSS). لا يشغّل Python ولا يفتح منفذًا للاستماع. |
| **GitHub Actions** | ❌ | بيئة مؤقتة (ephemeral) للمهام القصيرة، تُدمَّر بعد انتهائها، بحد أقصى 6 ساعات، وبلا عنوان دخول (inbound) ثابت. غير صالحة لخادم دائم. |
| **GitHub (Repo/CI)** | ✅ (دوره الصحيح) | التخزين، البناء الآلي (CI)، والنشر الآلي (CD) إلى AWS و Pages. |

> **الخلاصة:** رصد يحتاج **عملية دائمة** (خادم HTTP + جدولة + قاعدة بيانات على القرص). هذا نموذج «خادم» لا «موقع ثابت»، وGitHub لا يوفّره. **الاستضافة تكون على AWS، وGitHub يبقى مصدر الكود وخط الأنابيب.**

*(نظريًا يمكن محاكاة الجمع عبر Actions مجدولة تكتب JSON إلى Pages، لكنه يلغي الـ API الحيّ والبحث والفلترة، ويكسر بنية المشروع الحالية — غير موصى به.)*

## 4. البنية المقترحة على AWS (خادم واحد، نطاق واحد)

أبسط بنية موثوقة، وتستفيد من استضافتك الحالية دون خادم إضافي:

```
                          الإنترنت
                             │  HTTPS (443)
                             ▼
              ┌──────────────────────────────┐
              │   Nginx / Caddy (Reverse Proxy)│  ← شهادة Let's Encrypt (مجانية)
              │   rasd.example.com             │
              └───────┬───────────────┬────────┘
        الملفات الثابتة │               │ /api/* (proxy_pass)
                        ▼               ▼
              ┌──────────────┐  ┌──────────────────┐
              │ frontend dist│  │ rasad-backend    │  ← حاوية Docker
              │ (build ثابت) │  │ FastAPI :8000    │
              └──────────────┘  │ + APScheduler    │
                                │ + SQLite (volume)│
                                └──────────────────┘

        ┌──────────────────────────────────────────┐
        │  cobalt (حاوية منفصلة، حدود موارد، منفذ آخر)│  ← معزول عن رصد
        └──────────────────────────────────────────┘
```

**لماذا خدمة النطاق الواحد (same-origin)؟**
- تُلغي مشاكل CORS (الواجهة والـ API على نفس النطاق) → لا حاجة لـ `allow_origins=["*"]`.
- شهادة HTTPS واحدة، وإدارة أبسط.
- الـ PWA يعمل بلا إعدادات إضافية.

> **بديل:** إبقاء الواجهة على **GitHub Pages** والـ API فقط على AWS (`api.rasd.example.com`). يعمل جيدًا لكنه يعيد إدخال CORS ويجعل الأصلين مختلفين. **موصى به فقط** إن أردت عرض نطاق GitHub المجاني للواجهة والاحتفاظ بحمل AWS في حدّه الأدنى.

## 5. المتطلّبات التقنية للتحويل

### 5.1 على مستوى البنية التحتية (AWS)

| المتطلّب | التفصيل | ضروري؟ |
|---|---|:---:|
| **عنوان IP ثابت** | Elastic IP (لديك بالفعل `18.133.11.77`، منطقة لندن `eu-west-2`). مجاني ما دام مرتبطًا بالخادم. | ✅ |
| **اسم نطاق (Domain)** | مثل `rasd.yourdomain.com`. يلزم لشهادة HTTPS وللوصول باسم بدل IP. (~10–15 $/سنة) | ✅ |
| **شهادة HTTPS** | Let's Encrypt عبر Caddy (تلقائي) أو certbot. **مجانية**. إلزامية للـ PWA وللأمان. | ✅ |
| **Reverse Proxy** | Nginx أو **Caddy** (أبسط، HTTPS تلقائي). يخدم الواجهة + يوجّه `/api`. | ✅ |
| **Security Group** | فتح 80/443 فقط للعالم؛ 22 (SSH) مقيّد بعنوانك. **إغلاق 8000/3000** عن الخارج. | ✅ |
| **حدود موارد Docker** | `mem_limit` / `cpus` لكل حاوية لمنع `cobalt` من مزاحمة رصد على الموارد. | ✅ |
| **نسخ احتياطي** | مهمة cron يومية: نسخ `rasad.db` + رفعها إلى S3 (أو snapshot لـ EBS). | ✅ موصى بشدّة |
| **مراقبة/إبقاء التشغيل** | `restart: unless-stopped` (موجود في compose) + فحص صحة `/api/health` (موجود). | ✅ |

### 5.2 على مستوى الكود (تعديلات صغيرة مطلوبة)

1. **تقييد CORS:** استبدال `allow_origins=["*"]` بقائمة نطاقات الإنتاج (يُقرأ من متغيّر بيئة). *(بضعة أسطر)*
2. **حاوية إنتاج للواجهة:** حاليًا `frontend/Dockerfile` يشغّل `npm run dev` (خادم تطوير). يلزم **مرحلة بناء متعددة** تُنتج `dist/` وتخدمه Nginx/Caddy. *(Dockerfile قصير)*
3. **إزالة `--reload` من الـ Backend في الإنتاج** (موجود في Dockerfile الحالي) واستخدام عدة عمّال uvicorn بحذر (انظر تحذير SQLite أدناه).
4. **متغيّرات البيئة للإنتاج:** ضبط مفاتيح API الحقيقية (NewsAPI، OpenSky) ومسار DB في `.env` على الخادم (لا في المستودع).
5. **مسار قاعدة البيانات على Volume دائم:** لضمان بقاء البيانات عبر إعادة بناء الحاويات (compose يوفّر ذلك جزئيًّا — يجب توحيد مسار `data/`).

### 5.3 تقدير الموارد (الحِمل الفعلي)

رصد **خفيف جدًّا**؛ العبء الأساسي هو نداءات الشبكة الخارجية الدورية لا الحوسبة:

| المورد | الاستهلاك المتوقّع | ملاحظة |
|---|---|---|
| **الذاكرة (RAM)** | ~150–400 MB للـ Backend + ~50 MB للـ Nginx | صغير جدًّا |
| **المعالج (CPU)** | خامل معظم الوقت؛ نبضات قصيرة عند الجمع الدوري | لا يزاحم `cobalt` إن وُضعت الحدود |
| **القرص (Disk)** | قاعدة بيانات نصية تنمو ببطء (~عشرات–مئات MB/سنة) + ~200 MB للحاويات | لديك ~40 GB متاح → وفرة كبيرة |
| **عرض النطاق (Bandwidth)** | صادر: تحميل الواجهة مرّة (~بضعة MB مع تخزين PWA) + استجابات JSON صغيرة. البث لا يمرّ عبرك. | منخفض ما لم يتضخّم عدد الزوّار |

> **التعايش مع `cobalt`:** `cobalt` (محمّل الفيديو) كثيف على **عرض النطاق والقرص** بشكل متقطّع. رصد لا يتعارض معه وظيفيًّا، لكن يجب:
> - عزلهما في حاويتين منفصلتين بمنافذ مختلفة.
> - وضع `mem_limit`/`cpus` لكل منهما.
> - مراقبة القرص: تنزيلات `cobalt` قد تملأ الـ 40 GB المتبقية بسرعة، ما قد يُعطّل كتابة قاعدة بيانات رصد. **يُنصح بتنظيف دوري لمخرجات cobalt** أو فصلها على قرص/مجلد مستقل بحصة (quota).

## 6. اعتبارات التوسّع والأمان (مهمّة عند الفتح العام)

عند تحوّل رصد من «أداة شخصية» إلى «موقع عام»، تظهر مسائل لم تكن قائمة محليًّا:

### 6.1 قاعدة البيانات SQLite — متى تصبح عنق الزجاجة؟
- ممتازة لنسخة واحدة وقراءات كثيرة (وهو نمط رصد الغالب: يجمع الخادم، ويقرأ الزوّار).
- **قيدها:** كاتب واحد في اللحظة. مع الجدولة المستمرة + زوّار كثيرين قد تظهر أخطاء `database is locked`.
- **التوصية:** ابدأ بـ SQLite (بسيط، يعمل الآن). **جهّز مسار ترحيل إلى PostgreSQL** إن تجاوزت البيانات ملايين الصفوف أو تجاوز الزوّار العشرات المتزامنين. SQLAlchemy يجعل هذا الترحيل مباشرًا.

### 6.2 حدود مفاتيح API الخارجية
- **NewsAPI (الخطة المجانية):** ~100 طلب/يوم و بيانات متأخّرة 24 ساعة — قد لا تكفي موقعًا عامًّا. قد يلزم ترقية مدفوعة.
- **OpenSky:** حصص للحساب المجاني؛ التطبيق يجمع كل 30 ثانية أصلًا. مع موقع عام، الحصة تُستهلك على مستوى الخادم لا المستخدم — يجب المراقبة.
- **المبدأ:** بما أنّ الجمع يتم مركزيًّا في الخادم (لا من متصفّح كل زائر)، فإنّ **الحصص لا تتضاعف بعدد الزوّار** — نقطة إيجابية للتصميم الحالي.

### 6.3 الأمان
- HTTPS إلزامي (Let's Encrypt).
- تقييد CORS و SSH.
- إخفاء `/docs` (Swagger) أو حمايته في الإنتاج إن لم يكن مطلوبًا للعامة.
- تحديد معدّل الطلبات (rate limiting) على مستوى Nginx/Caddy لمنع الإساءة.
- لا توجد مصادقة مستخدمين حاليًّا — إن أردت لوحة خاصة، يلزم إضافة طبقة تسجيل دخول (خارج نطاق التحويل الأساسي).

### 6.4 القانوني/الأخلاقي
- عند النشر العام، راجع شروط استخدام كل مصدر بيانات (GDELT/NewsAPI/UCDP) بخصوص إعادة النشر العام، وأضف نسب المصادر (attribution) في الواجهة.

## 8. مصفوفة القرار: أين يعيش كل مكوّن؟

| المكوّن | التوصية | البديل |
|---|---|---|
| **مصدر الكود + CI/CD** | GitHub (Repo + Actions) | — |
| **الواجهة (Static)** | AWS خلف نفس النطاق (أبسط، بلا CORS) | GitHub Pages (مجاني، لكن يعيد CORS) |
| **الخادم (FastAPI + جدولة)** | **AWS (حاوية Docker)** — إلزامي | لا بديل على GitHub |
| **قاعدة البيانات** | SQLite على Volume في AWS الآن | PostgreSQL عند التوسّع |
| **النطاق + HTTPS** | AWS + Let's Encrypt | Cloudflare أمام AWS (يضيف CDN + حماية) |

## 10. الخلاصة والتوصية

1. **التحويل مُجدٍ وموصى به** — البنية جاهزة تقريبًا، والتكلفة الإضافية ضئيلة.
2. **الـ Backend على AWS** (حاوية Docker خلف Reverse Proxy)، و**GitHub لخط الأنابيب فقط** (كود + بناء + نشر). لا يمكن استضافة الخادم على GitHub.
3. **استضافتك الحالية تكفي** بوفرة لموارد رصد، بشرط **عزل `cobalt`** بحدود موارد ومراقبة القرص.
4. **الأولوية التقنية الأولى:** النطاق + HTTPS + Reverse Proxy + Dockerfile إنتاجي للواجهة + تقييد CORS. هذه هي الفجوة الحقيقية بين «يعمل محليًّا» و«موقع عام آمن».
5. **راقب لاحقًا:** حصص API الخارجية، وقفل SQLite عند نمو الزوّار — مع مسار ترحيل جاهز إلى PostgreSQL.

> **بعبارة واحدة:** انقل الخادم كما هو إلى AWS داخل Docker، ضَع Caddy أمامه لـ HTTPS تلقائي، اجعل GitHub Actions ينشر تلقائيًّا، واعزل cobalt — تحصل على «رصد» موقعًا إلكترونيًّا بأقلّ تغيير في الكود وأقلّ كلفة.
